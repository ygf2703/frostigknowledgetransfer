weekly-reportדוח שבועי אחיד למנהל או ללקוח▾ הועתק ✓ 
---
name: weekly-report
description: Write a weekly status report in a fixed structure.
---

Use this skill when the user asks for a weekly report.

Inputs to collect (ask once, together, if missing): the week's achievements, open items, next week's plan, and the audience (manager or client).

Process:
1. Open with a two-sentence summary: state of the week and the single most important thing to know.
2. Achievements as bullets, each with a fact (number, deliverable, date).
3. Open items with an owner per item; next steps with a real date per step.
4. For a client audience, drop internal jargon and add one line on what you need from them.

Output: a one-page report in the fixed structure above.

Boundaries: no superlatives, no invented progress. If an item was not provided, write "טרם עודכן" instead of guessing.

Before presenting, check: every open item has an owner, every next step has a date, and the summary matches the bullets.

Example - a marketing project manager sends a client: "השבוע: עלתה קמפיין החורף (3 ערוצים), אושרו 5 מודעות. פתוח: חומרי וידאו - לקוח, עד 29.10. בשבוע הבא: דוח ביצועים ראשון ב-3.11."

---
name: meeting-notes
description: Summarize meeting notes or a transcript into decisions, action items, owners and due dates.
---

Use this skill when the user shares meeting notes or a transcript and asks for a summary.

Inputs to collect: the notes or transcript, and the meeting's goal if it is not obvious from the material.

Process:
1. Extract decisions, action items, and open questions separately - do not mix them.
2. Every action item gets task / owner / due date. If the transcript does not name an owner or a date, mark TBD - never assign one by guessing who spoke last.
3. Add a three-line context summary at the top for someone who was not in the room.

Output: decisions (bullets), an action-items table (task / owner / due), open questions. Under one page.

Boundaries: summarize only what was said. If a discussion had no conclusion, write "לא הוחלט" rather than picking the option you prefer.

Before presenting, check: each action item appears in the source, and each decision has the condition or reason if one was stated.

Example - product sprint planning: "הוחלט: השקה ב-15.11 בלי תכונת הייבוא. משימות: דנה - מסך הגדרות עד 28.10; יוסי - בדיקות רגרסיה עד 3.11. פתוח: מחיר חבילת צוות."

---
name: inbox-triage
description: Classify a list of emails by urgency and suggest next actions.
---

Use this skill when the user asks to sort or prioritize a list of emails.

Inputs to collect: the email list (sender, subject, snippet or body per email) and what the user cares about right now (e.g. a launch this week, waiting on a signature).

Process:
1. Classify each email into exactly one bucket: reply today / delegate / schedule / archive.
2. Give one line of reasoning per email, tied to the user's stated priorities.
3. Draft a two-to-three sentence reply for every "reply today" item, in the user's tone.
4. Close with a count per bucket so the user can sanity-check the sweep at a glance.

Output: the four buckets with reasoning, plus the reply drafts.

Boundaries: if you can only see subjects and not bodies, say so and classify provisionally. Never suggest archiving a thread from a person the user flagged as important.

Before presenting, check: every email appears exactly once, and the bucket counts match the list length.

Example - a lawyer on Monday morning: 41 emails -> 6 reply today (2 client deadlines), 9 to delegate to the associate, 12 scheduled for Wednesday, 14 archived newsletters.
sprint-plannerפירוק פרויקט למשימות שבועיות▾ הועתק ✓ 
---
name: sprint-planner
description: Break a project into milestones and weekly tasks with dependencies.
---

Use this skill when the user describes a project and asks for a work plan.

Inputs to collect: the project goal, the deadline, who is working on it, and hard constraints (budget, dependencies on others, holidays).

Process:
1. Work backward from the deadline to 3-6 milestones with dates.
2. Break each milestone into weekly tasks; mark which task blocks which.
3. Add a rough effort per task (S/M/L) and name the owner if known.
4. End with the first three actions to start this week.

Output: a milestone table (milestone / date / tasks / owner / effort) plus the dependency list.

Boundaries: say explicitly that effort estimates are rough. If the deadline looks unrealistic for the scope, say so and propose what fits - do not silently compress.

Before presenting, check: no task depends on a later task, and the plan actually reaches the goal.

Example - launching a Shopify store in 6 weeks: milestones = catalog ready (week 2), design done (week 3), payments+shipping live (week 4), soft launch (week 5), public launch (week 6).

description: Record project decisions with context, options and rationale.
---

Use this skill when the user wants to record or revisit a project decision.

Inputs to collect: what was decided, by whom, and when. The options that were on the table, if the user remembers them.

Process:
1. Write one entry per decision: date, one-sentence context, options considered, the choice, the reason, the decider.

ab-test-readקריאת תוצאות מבחן A/B בלי מסקנות שווא▾ הועתק ✓ 
---
name: ab-test-read
description: Read A/B test results with unit-of-analysis, denominator and maturity checks.
---

Use this skill when the user shares A/B test results.

Inputs to collect: the metric per variant, sample size per variant, the primary metric decided before the test, and how users were assigned.

Process:
1. Check the unit of independence: if the same user appears in both variants or many times in one, per-pageview numbers overstate the evidence. Flag it.
2. Check denominators: conversion of what - visitors, sessions, clicks?
3. Check maturity: was the test stopped at a planned point or peeked at until it looked good? Early wins regress.
4. Compute the significance calculation from the counts, or request the success counts if they are missing. Without a calculation, no winner can be declared - state that as a limitation, not as a verdict.

Output: the evidence summary, what can and cannot be concluded, and the options (ship / iterate / drop / keep running) - "keep running" only after the design checks above pass, and only up to the planned sample, not beyond it.

Boundaries: never declare a winner from raw percentages alone. There is no universal minimum test length - maturity depends on traffic, effect size, and cycles of the business.

Before presenting, check: the conclusion follows from the computed evidence, not from the direction the user hoped for.

Example - a signup-button test: A = 96 signups / 1,200 visitors (8.0%), B = 105 / 1,180 (8.9%). Independence and denominators check out, but the difference is about z=0.78 - not significant at common levels. Conclusion: with this data no winner can be declared. If the design is sound and the planned sample has not been reached, the option is to continue to the plan; if it has, the honest verdict is no detectable difference.
cohort-retentionניתוח שימור לפי קוהורטים עם הגדרות מפורשות▾ הועתק ✓ 
---
name: cohort-retention
description: Analyze retention by signup cohort with explicit active and maturity definitions.
---

Use this skill when the user asks about retention or churn over time.

Inputs to collect: the user activity data, and - critically - the definition of "active" for this business (logged in? paid? completed an action?). If the user has not defined it, propose one and confirm before computing.

Process:
1. Group users by signup week or month. The denominator of every cell is that cohort's size - state it.
2. Compute the active share per cohort per period.
3. Interpret only mature cohorts: a cohort that has not yet reached week 4 has no week-4 retention. Mark young cohorts as "מוקדם מדי".
4. Compare slopes, not just first cells: improving retention flattens the curve.

Output: the cohort table with the definitions used, and the reading.

Boundaries: never fill future cells by extrapolation. If the activity definition changes mid-analysis, restart with the new definition.

Before presenting, check: every percentage's denominator is the cohort size, and no immature cohort is quoted as a trend.

Example - an app: the Jan cohort (n=412) shows 38% active at week 4, the Mar cohort (n=505) shows 46%. Observed week-4 retention is higher in the later cohort. Before crediting the February onboarding change, check confounders: acquisition-channel mix, seasonality, and other product changes in the window. Two cohorts at one week do not establish a trend or its cause.
